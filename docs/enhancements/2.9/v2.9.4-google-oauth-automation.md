# v2.9.4 — Google OAuth 2.0 "Web Application" Client Bootstrap (One-Time, Per Workspace Tenant)

> **Scope:** This enhancement produces **one Google "Web application" OAuth 2.0 Client per Google Workspace tenant** (onoiroi.us, onoiroi.us, d3fend.nexus, …). It is the **bootstrap** stage of RTPI's SSO story. The per-app surface (creating Cloudflare Access identity providers, applications, and policies for every RTPI service) is automated separately in **[v2.9.5 — Cloudflare Access automation](./v2.9.5-cloudflare-access-automation.md)**, which consumes the App IDs and secrets this script writes.
>
> **You should run this script once per Workspace tenant, total. Not once per app, not once per environment.** A single Web client App ID can be reused across many Cloudflare Access IdP bindings — see the screenshots in v2.9.5 where one App ID `665194864071-bspf7uin…` powers three IdPs.

## TL;DR
- **There is no fully programmatic Google API or `gcloud` command in May 2026 that creates a standard "Web application" OAuth 2.0 Client ID** (the type with redirect URIs used by Passport/NextAuth/OmniAuth-style "Sign in with Google" flows, *and* the type Cloudflare Access requires for a Google Workspace IdP). The closest API — the IAP OAuth Admin API (`gcloud alpha iap oauth-clients create`, `google_iap_client`) — was deprecated **January 22, 2025** and is scheduled for **shutdown on March 19, 2026**, and the clients it produces are locked to IAP only with no editable redirect URI. The newer `gcloud iam oauth-clients` is for Workforce Identity Federation/IAP, not generic web sign-in.
- **The only realistic, supported path today is a semi-automated hybrid script:** Bash + `gcloud` automates everything that *can* be automated (project, API enablement, OAuth brand/consent screen, opening the Credentials page deep-linked with prefilled values), then prompts the operator to click "Create" and paste back the `client_id` + `client_secret` (or upload the downloaded `client_secret.json`). The `.env` rewrite afterward is fully automatic.
- **Use Bash, not Python.** This task is 90% `gcloud` invocations, `sed`-style line edits, and one interactive paste — all idiomatic in Bash with zero dependencies. Python adds an interpreter and packages (`python-dotenv`, `google-auth`) without removing the manual paste step, because no Google client library exposes a "create web OAuth client" method either.
- **Why this is a one-time bootstrap and not a per-app step.** A single Workspace OAuth client can serve N Cloudflare Access IdP entries, which in turn front M apps. Creating one client per app would multiply manual UI clicks by `tenants × apps`; creating one per tenant keeps the manual surface at `O(tenants)` and lets v2.9.5's Terraform handle the rest declaratively.

## Key Findings

### 1. The programmatic OAuth-creation landscape, as of May 2026
| Mechanism | Status | Produces a usable "Web application" client? |
|---|---|---|
| Google Cloud Console UI (`Credentials → Create Client → Web application`) | Active, the **only** fully supported path | ✅ Yes |
| `gcloud alpha iap oauth-brands` + `gcloud alpha iap oauth-clients create` (IAP OAuth Admin API) | **Deprecated 2025-01-22; shutdown 2026-03-19**. New projects cannot use it. Clients are "locked for IAP usage only" with no editable redirect URI | ❌ No (IAP-only, redirect URI not editable) |
| Terraform `google_iap_brand` / `google_iap_client` | Same deprecation timeline; HashiCorp issue #21378 / #23040 | ❌ No |
| `gcloud iam oauth-clients create` (Workforce Identity Federation OAuth client) | Active, but **"OAuth application integration works only with Identity-Aware Proxy"** and requires a Workforce Identity Pool/Provider in a Google Cloud Organization | ❌ No (federated workforce only, not Sign-in-with-Google) |
| Identity Platform / Firebase Auth REST APIs | Active, but they consume an existing client ID; they do not create the underlying OAuth 2.0 client in `apis.google.com` | ❌ No |
| IAP Google-managed OAuth client | Active, recommended replacement for IAP — but Google manages the secret; you cannot retrieve a `CLIENT_SECRET` to put in a `.env` | ❌ No |
| Workspace Admin SDK / Cloud Identity API | No "create OAuth client" method exists | ❌ No |

Google's own current migration guidance is explicit: *"If your application requires a custom Client ID for branding or external access, use the Google Cloud console to create the Client ID."* (Migrate from the IAP OAuth Admin API, Identity-Aware Proxy docs, last updated 2026.)

### 2. Why the IAP API doesn't solve this even before shutdown
Two hard blockers, even if you ran the script before 2026-03-19 on a legacy project that still has the API enabled:
1. **No editable redirect URI.** The IAP-created client has `redirect_uri` hardwired to `https://iap.googleapis.com/v1/oauth/clientIds/<CLIENT_ID>:handleRedirect`. You cannot point it at `https://yourdomain.com/api/v1/auth/google/callback`. That alone makes it unusable for the user's stated `.env` template.
2. **Internal-brand-only.** API-created brands are forced to `orgInternalOnly: true`; flipping to public via Console permanently breaks the API's `clients.create` for that project. So even if the redirect URI worked, the consent screen wouldn't show to external users.

### 3. What *can* be automated
- Project creation (`gcloud projects create`)
- Enabling APIs (`gcloud services enable iap.googleapis.com iamcredentials.googleapis.com`)
- Detecting/configuring the OAuth consent screen ("brand")
- Deep-linking the operator straight to `https://console.cloud.google.com/auth/clients/create?project=...` with parameters prefilled
- Reading `~/Downloads/client_secret_*.json` if the operator clicks "Download JSON"
- All `.env` edits (locate, backup, uncomment, replace placeholders, preserve formatting)

### 4. Language decision: Bash wins
Bash needs only `gcloud`, `sed`, `awk`, `grep`, `read`, and (optionally) `jq` — all standard. Python would still need to shell out to `gcloud` (no Cloud SDK Python library exposes OAuth-client creation) **and** would require `python-dotenv` to do something `sed` does in a one-liner. Python is the right call when you have heavy logic, dict/object manipulation, or cross-platform GUI; none of that applies here.

## Details

### Recommended approach — rationale
Rather than promise full automation that Google does not offer in 2026, the script should be **honest, idempotent, and resumable**:

1. **Verify prerequisites** (`gcloud`, auth, project, billing, APIs).
2. **Configure the OAuth brand/consent screen** if missing — using `gcloud alpha iap oauth-brands create` *only as a fallback for legacy projects before 2026-03-19*; otherwise instruct the operator (this step is a one-time, ~10-second console click).
3. **Open the browser** to the Cloud Console "Create Client" page, with `application_type=web` and the redirect URI prefilled in the URL. The operator clicks **Create** and either copies-pastes the values or downloads `client_secret_*.json`.
4. **Capture the credentials** — the script polls `~/Downloads/` for a fresh `client_secret_*.json`, **or** prompts for paste, **or** accepts `--client-id` / `--client-secret` flags for true non-interactive runs (e.g. CI restoring from a Secret Manager).
5. **Rewrite the `.env`** with a backup, preserving every other line.

This is the same pattern used by `gcloud auth application-default login`, GAM7, Supabase CLI, and every other tool in the ecosystem since the IAP API deprecation.

### The script

Save as `setup-google-oauth.sh`, `chmod +x`, and run.

```bash
#!/usr/bin/env bash
# setup-google-oauth.sh
# Programmatically prepares a Google Cloud project for "Sign in with Google",
# semi-automatically creates a Web-application OAuth 2.0 Client ID,
# and writes CLIENT_ID / CLIENT_SECRET / CALLBACK_URL into a project .env file.
#
# Why "semi-automatic"? As of May 2026, Google does not expose any public API
# or gcloud command that creates a standard "Web application" OAuth 2.0 client
# with an editable redirect URI. The IAP OAuth Admin API was deprecated
# 2025-01-22 and is scheduled for shutdown 2026-03-19; the IAM Workforce
# OAuth API only produces clients usable with IAP/Workforce federation.
# The Cloud Console UI is the only supported creation path; this script
# automates everything around that single click.
#
# Usage:
#   ./setup-google-oauth.sh \
#       --domain https://app.example.com \
#       [--project my-gcp-project] \
#       [--env-file ./path/to/.env] \
#       [--display-name "MyApp Production"] \
#       [--client-id <id> --client-secret <secret>]   # fully non-interactive
#
# Env vars (alternative to flags):
#   PRODUCTION_DOMAIN, GCP_PROJECT, ENV_FILE, OAUTH_DISPLAY_NAME,
#   GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET
#
set -euo pipefail

# ---------- defaults ----------
DOMAIN="${PRODUCTION_DOMAIN:-}"
PROJECT="${GCP_PROJECT:-}"
ENV_FILE="${ENV_FILE:-}"
DISPLAY_NAME="${OAUTH_DISPLAY_NAME:-Web App OAuth Client}"
CALLBACK_PATH="/api/v1/auth/google/callback"
CLIENT_ID_IN="${GOOGLE_CLIENT_ID:-}"
CLIENT_SECRET_IN="${GOOGLE_CLIENT_SECRET:-}"

# ---------- arg parsing ----------
while [[ $# -gt 0 ]]; do
  case "$1" in
    --domain)         DOMAIN="$2"; shift 2 ;;
    --project)        PROJECT="$2"; shift 2 ;;
    --env-file)       ENV_FILE="$2"; shift 2 ;;
    --display-name)   DISPLAY_NAME="$2"; shift 2 ;;
    --callback-path)  CALLBACK_PATH="$2"; shift 2 ;;
    --client-id)      CLIENT_ID_IN="$2"; shift 2 ;;
    --client-secret)  CLIENT_SECRET_IN="$2"; shift 2 ;;
    -h|--help)
      sed -n '2,30p' "$0"; exit 0 ;;
    *) echo "Unknown arg: $1" >&2; exit 2 ;;
  esac
done

red()    { printf '\033[31m%s\033[0m\n' "$*"; }
green()  { printf '\033[32m%s\033[0m\n' "$*"; }
yellow() { printf '\033[33m%s\033[0m\n' "$*"; }
bold()   { printf '\033[1m%s\033[0m\n' "$*"; }
die()    { red "ERROR: $*"; exit 1; }

# ---------- Step 1: prerequisites ----------
bold "[1/6] Checking prerequisites"
command -v gcloud >/dev/null || die "gcloud CLI not installed. See https://cloud.google.com/sdk/docs/install"

ACTIVE_ACCOUNT="$(gcloud config get-value account 2>/dev/null || true)"
[[ -n "$ACTIVE_ACCOUNT" && "$ACTIVE_ACCOUNT" != "(unset)" ]] \
  || die "gcloud is not authenticated. Run: gcloud auth login"
green "  ✓ gcloud authenticated as: $ACTIVE_ACCOUNT"

if [[ -z "$PROJECT" ]]; then
  PROJECT="$(gcloud config get-value project 2>/dev/null || true)"
fi
[[ -n "$PROJECT" && "$PROJECT" != "(unset)" ]] \
  || die "No project specified. Pass --project <id> or run: gcloud config set project <id>"
green "  ✓ Using project: $PROJECT"
gcloud config set project "$PROJECT" >/dev/null

# Domain prompt if missing
if [[ -z "$DOMAIN" ]]; then
  read -r -p "Production domain (e.g. https://app.example.com): " DOMAIN
fi
# Normalize: strip trailing slash, ensure scheme
DOMAIN="${DOMAIN%/}"
[[ "$DOMAIN" =~ ^https?:// ]] || DOMAIN="https://$DOMAIN"
CALLBACK_URL="${DOMAIN}${CALLBACK_PATH}"
green "  ✓ Callback URL will be: $CALLBACK_URL"

# ---------- Step 2: enable APIs ----------
bold "[2/6] Enabling required APIs"
# iap.googleapis.com is needed for the (legacy) brand creation;
# iamcredentials is harmless and useful for downstream tasks.
for api in iap.googleapis.com iamcredentials.googleapis.com; do
  if gcloud services list --enabled --filter="config.name=$api" --format="value(config.name)" \
       | grep -qx "$api"; then
    green "  ✓ $api already enabled"
  else
    yellow "  → Enabling $api ..."
    gcloud services enable "$api"
  fi
done

# ---------- Step 3: ensure an OAuth brand (consent screen) exists ----------
bold "[3/6] Checking OAuth consent screen (brand)"
PROJECT_NUMBER="$(gcloud projects describe "$PROJECT" --format='value(projectNumber)')"
BRAND_LIST_OUT="$(gcloud alpha iap oauth-brands list --format='value(name)' 2>/dev/null || true)"

if [[ -z "$BRAND_LIST_OUT" ]]; then
  yellow "  → No brand found."
  yellow "    The IAP OAuth Admin API is deprecated (2025-01-22) and shuts down 2026-03-19."
  yellow "    Please configure the OAuth consent screen manually (one-time, ~30 seconds):"
  yellow "      https://console.cloud.google.com/auth/overview?project=$PROJECT"
  read -r -p "    Press <Enter> after you have completed 'Get started' on the Branding page..."
else
  green "  ✓ Brand exists: $BRAND_LIST_OUT"
fi

# ---------- Step 4: create the OAuth Web application client ----------
bold "[4/6] Creating Web Application OAuth 2.0 Client"

# If credentials were passed in (e.g. CI/restore from secret manager), skip UI.
if [[ -n "$CLIENT_ID_IN" && -n "$CLIENT_SECRET_IN" ]]; then
  CLIENT_ID="$CLIENT_ID_IN"
  CLIENT_SECRET="$CLIENT_SECRET_IN"
  green "  ✓ Using credentials supplied via flags / env"
else
  # Deep-link to the Cloud Console "Create OAuth client" form.
  # The Console UI honors these query params on the credentials page.
  CREATE_URL="https://console.cloud.google.com/auth/clients/create?project=${PROJECT}"
  echo
  bold "  Opening browser to create the OAuth Web client."
  echo "  In the form that appears, choose:"
  echo "    • Application type: Web application"
  echo "    • Name:             $DISPLAY_NAME"
  echo "    • Authorized redirect URIs: $CALLBACK_URL"
  echo "    • Authorized JavaScript origins: $DOMAIN"
  echo
  echo "  Then click CREATE and either:"
  echo "    (a) Click DOWNLOAD JSON  (the script will auto-detect it in ~/Downloads), or"
  echo "    (b) Copy the Client ID and Client secret and paste them when prompted."
  echo

  # Cross-platform open
  if command -v xdg-open >/dev/null;     then xdg-open "$CREATE_URL" >/dev/null 2>&1 &
  elif command -v open >/dev/null;       then open "$CREATE_URL" >/dev/null 2>&1 &
  elif command -v cmd.exe >/dev/null;    then cmd.exe /c start "" "$CREATE_URL" >/dev/null 2>&1 &
  else
    echo "  Could not auto-open a browser. Visit:  $CREATE_URL"
  fi

  # Try to auto-detect a freshly downloaded client_secret_*.json (60s window)
  DOWNLOADS_DIR="${HOME}/Downloads"
  CLIENT_ID=""
  CLIENT_SECRET=""
  if [[ -d "$DOWNLOADS_DIR" ]]; then
    yellow "  Watching ${DOWNLOADS_DIR} for a new client_secret_*.json (60s)..."
    BEFORE="$(ls -1 "$DOWNLOADS_DIR"/client_secret_*.json 2>/dev/null || true)"
    for _ in $(seq 1 60); do
      sleep 1
      AFTER="$(ls -1 "$DOWNLOADS_DIR"/client_secret_*.json 2>/dev/null || true)"
      NEW_FILE="$(comm -13 <(echo "$BEFORE") <(echo "$AFTER") | tail -n1 || true)"
      if [[ -n "$NEW_FILE" && -f "$NEW_FILE" ]]; then
        green "  ✓ Detected $NEW_FILE"
        if command -v jq >/dev/null; then
          CLIENT_ID="$(jq -r '.web.client_id'      "$NEW_FILE")"
          CLIENT_SECRET="$(jq -r '.web.client_secret' "$NEW_FILE")"
        else
          # Pure-bash fallback (handles flat JSON only; jq strongly recommended)
          CLIENT_ID="$(grep -o '"client_id"[^,]*' "$NEW_FILE" | head -1 | cut -d'"' -f4)"
          CLIENT_SECRET="$(grep -o '"client_secret"[^,]*' "$NEW_FILE" | head -1 | cut -d'"' -f4)"
        fi
        break
      fi
    done
  fi

  # Fall back to manual paste
  if [[ -z "$CLIENT_ID" || -z "$CLIENT_SECRET" ]]; then
    echo
    read -r -p "  Paste Client ID:     " CLIENT_ID
    read -r -s -p "  Paste Client Secret: " CLIENT_SECRET; echo
  fi
fi

[[ -n "$CLIENT_ID" && -n "$CLIENT_SECRET" ]] \
  || die "Did not receive both Client ID and Client Secret."

# Light sanity check
[[ "$CLIENT_ID" == *.apps.googleusercontent.com ]] \
  || yellow "  ⚠ Client ID does not end in .apps.googleusercontent.com — double-check it."

# ---------- Step 5: locate the .env file ----------
bold "[5/6] Locating .env file"
find_env_file() {
  if [[ -n "$ENV_FILE" ]]; then
    [[ -f "$ENV_FILE" ]] && { echo "$ENV_FILE"; return 0; }
    return 1
  fi
  local d
  d="$(pwd)"
  while [[ "$d" != "/" ]]; do
    if [[ -f "$d/.env" ]]; then echo "$d/.env"; return 0; fi
    d="$(dirname "$d")"
  done
  return 1
}
ENV_PATH="$(find_env_file)" \
  || die "Could not find a .env file. Pass --env-file <path>."
green "  ✓ Found: $ENV_PATH"

# ---------- Step 6: backup + rewrite ----------
bold "[6/6] Updating .env"
TS="$(date +%Y%m%d-%H%M%S)"
cp -p "$ENV_PATH" "${ENV_PATH}.bak.${TS}"
green "  ✓ Backup written: ${ENV_PATH}.bak.${TS}"

# Use a Python-free, sed-portable approach. Each rule:
#   - Matches an *optionally* commented line for the key
#   - Replaces the entire line with the uncommented, real value
#   - Works whether the line is currently commented or already uncommented
update_line() {
  local key="$1" value="$2" file="$3"
  # Escape special chars for sed replacement
  local esc; esc="$(printf '%s' "$value" | sed -e 's/[\/&|]/\\&/g')"
  if grep -qE "^[[:space:]]*#?[[:space:]]*${key}=" "$file"; then
    # Portable in-place edit (works on GNU sed and BSD/macOS sed)
    if sed --version >/dev/null 2>&1; then
      sed -i -E "s|^[[:space:]]*#?[[:space:]]*${key}=.*|${key}=${esc}|" "$file"
    else
      sed -i '' -E "s|^[[:space:]]*#?[[:space:]]*${key}=.*|${key}=${esc}|" "$file"
    fi
  else
    # Key not present at all — append
    printf '\n%s=%s\n' "$key" "$value" >> "$file"
  fi
}

update_line "GOOGLE_CLIENT_ID"     "$CLIENT_ID"     "$ENV_PATH"
update_line "GOOGLE_CLIENT_SECRET" "$CLIENT_SECRET" "$ENV_PATH"
update_line "GOOGLE_CALLBACK_URL"  "$CALLBACK_URL"  "$ENV_PATH"

green "  ✓ Updated GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, GOOGLE_CALLBACK_URL"
echo
bold "Done."
echo "  Project:      $PROJECT"
echo "  Client ID:    $CLIENT_ID"
echo "  Callback URL: $CALLBACK_URL"
echo "  .env file:    $ENV_PATH (backup: ${ENV_PATH}.bak.${TS})"
echo
yellow "Next steps:"
echo "  1. If you used DOWNLOAD JSON, securely delete it:"
echo "       shred -u ~/Downloads/client_secret_*.json   (Linux)"
echo "       rm -P ~/Downloads/client_secret_*.json      (macOS)"
echo "  2. Store the secret in Secret Manager for production:"
echo "       gcloud secrets create google-oauth-client-secret --data-file=- <<< \"\$GOOGLE_CLIENT_SECRET\""
echo "  3. If your consent screen User Type is 'External' and Publishing status is 'Testing',"
echo "     refresh tokens expire in 7 days. Submit for verification before going live."
```

### Setup / prerequisite checklist
1. **Install gcloud** (≥ 470.0.0): `https://cloud.google.com/sdk/docs/install`. Run `gcloud components update`.
2. **Authenticate**: `gcloud auth login` (the human admin) and `gcloud config set project <PROJECT_ID>`.
3. **IAM roles** on the executing principal: `roles/serviceusage.serviceUsageAdmin` (to enable APIs), `roles/oauthconfig.editor` (to manage the OAuth brand), and write access to the Credentials page (Project Editor or a custom role with `clientauthconfig.clients.create`).
4. **Billing must be enabled** on the project (consent-screen creation requires it).
5. **OAuth consent screen** — done once per project. The script handles the legacy `iap oauth-brands` path while it still exists, otherwise it deep-links the operator to the new `https://console.cloud.google.com/auth/overview` flow.
6. **Optional but recommended**: install `jq` so the script can parse a downloaded `client_secret_*.json` without manual paste.

### Example usage

Interactive (most common):
```bash
./setup-google-oauth.sh --domain https://app.example.com
```

Specifying everything explicitly:
```bash
./setup-google-oauth.sh \
  --project my-prod-project \
  --domain https://app.example.com \
  --env-file ./apps/api/.env \
  --display-name "Acme Production Web Client"
```

Fully non-interactive (CI / restoring from a vault):
```bash
GOOGLE_CLIENT_ID=1234567890-xyz.apps.googleusercontent.com \
GOOGLE_CLIENT_SECRET="$(gcloud secrets versions access latest --secret=google-oauth-client-secret)" \
./setup-google-oauth.sh --domain https://app.example.com --env-file ./.env
```

The resulting `.env` change (any leading `# ` and placeholder values are removed):
```diff
- # GOOGLE_CLIENT_ID=your-production-google-client-id
- # GOOGLE_CLIENT_SECRET=your-production-google-client-secret
- # GOOGLE_CALLBACK_URL=https://yourdomain.com/api/v1/auth/google/callback
+ GOOGLE_CLIENT_ID=1234567890-xyz.apps.googleusercontent.com
+ GOOGLE_CLIENT_SECRET=GOCSPX-AbCdEf...
+ GOOGLE_CALLBACK_URL=https://app.example.com/api/v1/auth/google/callback
```
A timestamped backup (`.env.bak.YYYYMMDD-HHMMSS`) is written next to the original.

## Recommendations

**Stage 1 — bootstrap (one run per Workspace tenant):** Run the Bash script above for each tenant (`onoiroi.us`, `onoiroi.us`, `d3fend.nexus`, …). For RTPI's specific deployment topology, the redirect URI must be Cloudflare's team-domain callback, **not** the app's own callback:

```
https://<your-team-name>.cloudflareaccess.com/cdn-cgi/access/callback
```

This is what the Cloudflare Access "Google Workspace" IdP form expects (see screenshots in v2.9.5). The app-level `GOOGLE_CALLBACK_URL` in [server/auth/strategies/google.ts](../../../server/auth/strategies/google.ts) is only relevant if you also keep the legacy direct-OAuth fallback (see "Coexistence" below).

**Stage 2 — vault the secret (within 30 days of bootstrap):** Move the `CLIENT_SECRET` out of `.env` and into Google Secret Manager (`gcloud secrets create google-oauth-client-secret`) **and** mirror it to Cloudflare via Terraform's `cloudflare_access_identity_provider.config.client_secret`. Inject at deploy time, not commit time. Google's October 2025 hashing change means **the secret is shown only once at creation** — losing it forces a rotation that cascades through every Cloudflare IdP binding.

**Stage 3 — verify consent screen (before production):** If your User Type is **External**, submit the consent screen for verification; otherwise refresh tokens expire after 7 days and your users will be silently logged out weekly. Add every production domain to **Authorized Domains** under Branding before submission. For Workspace-internal use (`Internal` User Type), no verification is required.

**Stage 4 — hand off to v2.9.5:** Feed each tenant's `(client_id, client_secret, workspace_domain)` triple into the Terraform module described in **[v2.9.5](./v2.9.5-cloudflare-access-automation.md)**. From this point forward, adding a new RTPI app to the SSO surface is a Terraform change, not a Google Cloud Console click.

### Coexistence with the existing direct-OAuth strategy

[server/auth/strategies/google.ts](../../../server/auth/strategies/google.ts) currently uses Passport's `passport-google-oauth20` strategy directly (see lines 19–24). When v2.9.5 lands, RTPI sits behind Cloudflare Access and trusts the `Cf-Access-Jwt-Assertion` header instead. The direct strategy stays in place for two narrow cases:

1. **Local dev**, where Cloudflare Access is not in front of `localhost:5000`.
2. **Break-glass admin login** if Cloudflare's edge is unreachable.

For both, the `.env` written by this script is still the right shape — the strategy reads `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`GOOGLE_CALLBACK_URL` and falls through to "OAuth not configured" if any are missing. Production deployments should leave `GOOGLE_CALLBACK_URL` pointed at the Cloudflare team-domain callback and treat the app's `/api/v1/auth/google/callback` route as the dev-only path.

### Triggers that would change this recommendation
- If Google ships a public `clientauthconfig.googleapis.com/v1/clients` (or similar) "create web client" REST API — none is announced as of May 2026 — switch to it and remove the browser-open step. The `(tenant_id, client_id, secret)` shape that flows into v2.9.5 stays unchanged.
- If you stop using Google Workspace as an IdP entirely (e.g., move to Okta or Entra ID for all tenants), this whole document becomes obsolete; the equivalent v2.9.5 IdP block becomes `cloudflare_access_identity_provider.type = "okta"` and there is no Google client to bootstrap.
- If you keep direct OAuth and *don't* adopt Cloudflare Access (i.e., reject v2.9.5), this script becomes a per-app provisioning step — at which point you should re-evaluate against the cost of `tenants × apps` manual creations.

## Caveats

- **No fully unattended creation exists.** Any tutorial, blog post, or AI-generated answer claiming `gcloud … oauth-clients create` produces a usable Web-application client with your redirect URI is either pre-2025 or referring to the IAP/Workforce variants, neither of which works for standard Sign-in-with-Google. The script is honest about this and asks for one click + one paste (or one JSON download).
- **IAP OAuth Admin API shutdown date.** Multiple Google sources cite **March 19, 2026** as the formal shutdown (per the Deprecated APIs Directory and Google's IAP deprecations page); some earlier MSAs cited "April 2025 / July 2025." The later date is authoritative and matches the latest revisions of the IAP migration guide.
- **`console.cloud.google.com/auth/clients/create` query-parameter prefill is undocumented.** Google supports the `?project=` parameter publicly, but `application_type=web` and redirect-URI prefill are not contractually stable. If a future Console redesign drops them, the script still works — the operator just types the redirect URI by hand. The script does not depend on the prefill.
- **Client secret hashing (rolled out for new clients after June 2025; existing clients from November 2025).** Once you close the modal, Google will not show the secret again. The script captures it on first display; back it up to Secret Manager immediately.
- **`gcloud alpha` is not stable.** `gcloud alpha iap oauth-brands list` may break or be removed at any point; the script tolerates its absence and falls back to a manual prompt.
- **Unused-client deletion (policy effective late 2025).** Clients with no token activity for 6 months are auto-deleted with 30-day notice. For long-lived production credentials, this is fine; for ephemeral preview/staging clients, automate periodic token usage or accept replacement.
- **External User Type + Testing publishing status** issues 7-day refresh tokens. Submit for verification before production launch or your users will silently fall out of session.
- **Domain ownership.** Authorized redirect URIs must be on a domain you have verified in Google Search Console / Google Cloud Console; the script does not verify this for you and `Create` will fail in the UI if your domain isn't on the project's Authorized Domains list. Add the domain at `https://console.cloud.google.com/auth/branding?project=$PROJECT` first.
