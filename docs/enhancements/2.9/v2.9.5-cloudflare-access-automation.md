# v2.9.5 — Cloudflare Access Automation (Multi-Tenant SSO + Authorization)

**Created:** 2026-05-04
**Status:** Planning
**Priority:** HIGH — replaces per-app Google OAuth wiring with declarative IaC; consumes [v2.9.4](./v2.9.4-google-oauth-automation.md) bootstrap output
**Feature flag:** `FF_CLOUDFLARE_ACCESS`

## Overview

Move RTPI's user-facing SSO and authorization layer from per-app Passport-Google strategies to **Cloudflare Access in front of every public RTPI service**, configured entirely via Terraform. The operator runs [v2.9.4's bootstrap script](./v2.9.4-google-oauth-automation.md) **once per Google Workspace tenant** to mint a single Web OAuth client; this release wires that client into N Cloudflare Access identity providers (one per tenant) and M Access applications (one per RTPI surface — main UI, API, Sysreptor, Docmost, Empire, Adaptix, Kasm, etc.) plus their authorization policies.

The end state matches what is already partially built in the operator's Cloudflare dashboard (see screenshots in conversation): three Google Workspace IdPs (`attck-workspace`, `c3s-Workspace`, `d3fend-Workspace`) — all sharing the **same Google App ID** `665194864071-bspf7uin…apps.googleusercontent.com`, each scoped to its own Workspace domain (`attck.nexus`, `c3s.nexus`, `d3fend.nexus`).

The work breaks into **6 phases**, all gated by `FF_CLOUDFLARE_ACCESS` except Phase 1 (Terraform skeleton, infra-only, has no runtime effect on RTPI itself). The migration is non-destructive: the existing direct Google OAuth strategy in [server/auth/strategies/google.ts](../../../server/auth/strategies/google.ts) stays in place as a localhost/break-glass fallback.

## Current State Analysis

### What v2.9.4 produces
For each Workspace tenant, one row of:
| Field | Example |
|---|---|
| `tenant_id` | `attck` |
| `workspace_domain` | `attck.nexus` |
| `google_client_id` | `665194864071-bspf7uin…apps.googleusercontent.com` |
| `google_client_secret` | `GOCSPX-…` (in Secret Manager / Cloudflare secret) |
| `cloudflare_account_id` | `<32-char hex>` |

These flow into v2.9.5 as the input variables of the Terraform module.

### What RTPI already does
- [server/auth/strategies/google.ts:9-13](../../../server/auth/strategies/google.ts#L9-L13) gates the Passport-Google strategy on `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` being set; if absent, the route is silently disabled. This means the Cloudflare-fronted production deployment can keep the env vars unset and the dev deployment can keep them set, with **no code change required**.
- [server/auth/middleware.ts](../../../server/auth/middleware.ts) currently relies on `req.session` populated by Passport. Phase 4 below adds a parallel `verifyCloudflareJWT` middleware that populates the same `req.user` shape from the `Cf-Access-Jwt-Assertion` header.
- [server/auth/strategies/local.ts](../../../server/auth/strategies/local.ts) and [server/auth/strategies/apikey.ts](../../../server/auth/strategies/apikey.ts) stay untouched — Cloudflare Access does not gate API-key requests (those are app-to-app).

### What's missing
- **No declarative IaC** for Access apps/policies/IdPs. The screenshots show three IdPs created by hand; the underlying applications and policies are entirely click-driven today.
- **No JWT verification on the RTPI side.** A user with the right `cloudflareaccess.com` cookie can reach the app, but RTPI does not yet read the identity headers Cloudflare injects (`Cf-Access-Authenticated-User-Email`, `Cf-Access-Jwt-Assertion`) — meaning the app still hits its own login page after passing Access.
- **No authorization-rule layering.** Internal-vs-operator-vs-admin RBAC lives in `users.role` in the DB. There is no group-based mapping from "Workspace group `red-team-leads`" → RTPI role `admin`.
- **No tenant isolation.** Three Workspace domains (attck, c3s, d3fend) share one RTPI deployment, so the JWT's `email` domain must drive a tenant claim consumed by row-level scoping (out of scope for this doc — tracked under v2.10 multi-tenancy).

## Architecture

### Request flow (post-v2.9.5)
```
User browser
  │
  ▼  (1) HTTPS to https://rtpi.attck.nexus
Cloudflare edge ──► Access enforces policy
  │                  • IdP: attck-workspace (Google)
  │                  • Allow:  email_domain == "attck.nexus"
  │                  • Require: group "rtpi-users"
  │                  • Reject otherwise → /cdn-cgi/access/login
  │
  ▼  (2) Authorized request, signed JWT in header
RTPI nginx / Express
  │
  ▼  (3) verifyCloudflareJWT middleware
  │       • fetches JWKS from <team>.cloudflareaccess.com/cdn-cgi/access/certs
  │       • validates signature, aud (Access app AUD tag), iss
  │       • extracts email + custom claims (groups)
  │       • upsert into users table (authMethod='cloudflare_access')
  │       • sets req.user
  ▼
Express routes (existing role-gated handlers run unchanged)
```

### Module layout
```
infra/
  cloudflare-access/
    main.tf             # provider, locals
    variables.tf        # tenants[], applications[], cloudflare_account_id
    idp.tf              # cloudflare_access_identity_provider per tenant
    applications.tf     # cloudflare_access_application + policy per app
    outputs.tf          # AUD tags (consumed by RTPI server env)
    terraform.tfvars.example
    README.md
```
The module is **standalone** (no dependency on the rest of RTPI's docker-compose / build) and runs from `infra/cloudflare-access/` with its own state — operators apply it from their workstation or a CD job, not from `npm run deploy:check`.

### Subdomain manifest is the source of truth

The hostnames protected by Access must agree with the hostnames build.sh provisions DNS records and TLS certs for. Both ends read from a single file:

[setup/services.manifest](../../../setup/services.manifest) — pipe-delimited, one row per public subdomain. Each row carries: `suffix | profile_gate | upstream_url | websocket | tls_upstream`. The shared parser in [setup/services_manifest.sh](../../../setup/services_manifest.sh) is sourced by [build.sh](../../../build.sh), [setup/cert_manager.sh](../../../setup/cert_manager.sh), and [setup/cloudflare_dns_manager.sh](../../../setup/cloudflare_dns_manager.sh) — they all iterate the same manifest, filtered by the active docker-compose profiles.

**Adding a new RTPI surface to the public Access perimeter is a two-line change:**

1. Append one row to `setup/services.manifest` (DNS + cert + nginx happen automatically on next `build.sh --enable-ssl` run).
2. Append one matching application to `terraform.tfvars` and `terraform apply` (Cloudflare Access app + policy).

No script edits, no nginx-template edits.

## Phases

### Phase 1 — Terraform skeleton (infra-only, no flag)
**Goal:** Land [infra/cloudflare-access/](../../../infra/cloudflare-access/) with provider config, variables, and a single example tenant + app, applied to a staging Cloudflare account. No RTPI server change.

- Create the module structure above.
- Pin `cloudflare/cloudflare` provider to `>= 4.40, < 5` (the v4 line stabilized `cloudflare_zero_trust_access_*` resources; v5 may rename).
- Variables: `cloudflare_account_id` (string), `tenants` (list of objects), `applications` (list of objects). See variables.tf in the sketch.
- Add `terraform.tfvars.example` with the three real tenants (attck/c3s/d3fend) but **no secrets** — secrets come from environment (`TF_VAR_…`) or `tfvars` files added to `.gitignore`.

**Acceptance:** `terraform plan` against the staging account produces a clean diff representing one IdP + one app + one policy.

### Phase 2 — Per-tenant IdP resources (`FF_CLOUDFLARE_ACCESS`)
**Goal:** For each entry in `var.tenants`, produce one `cloudflare_access_identity_provider` of type `google-apps`, configured exactly like the screenshots.

- Resource block reads `client_id`, `client_secret`, `apps_domain` from the tenant struct.
- `for_each = { for t in var.tenants : t.id => t }` so adding a fourth tenant is a one-line tfvars change.
- Outputs: `idp_ids[tenant_id]` (consumed by Phase 3 policy `include` blocks).

**Acceptance:** After apply, the Cloudflare Zero Trust dashboard shows IdPs identical in shape to the existing `attck-workspace`/`c3s-Workspace`/`d3fend-Workspace` entries — Name, App ID, Client secret, Workspace domain populated.

### Phase 3 — Per-app Access applications + policies (`FF_CLOUDFLARE_ACCESS`)
**Goal:** For each entry in `var.applications`, produce a `cloudflare_zero_trust_access_application` plus its `cloudflare_zero_trust_access_policy` set.

Each application has:
- `name`, `domain` (e.g. `rtpi.attck.nexus`), `tenant_id` (binds it to one Phase-2 IdP)
- `session_duration` (default `24h`)
- `auto_redirect_to_identity = true` (skip the IdP picker if only one is allowed)
- `allowed_idps = [idp_ids[tenant_id]]`
- A list of policy blocks: `decision = "allow"`, `include = [{ email_domain = workspace_domain }]`, optionally `require = [{ group = ["…"] }]`

**Acceptance:** With `terraform.tfvars.example` applied for the `attck` tenant, the dashboard shows 8 self-hosted Access applications matching the `setup/services.manifest` rows: `attck.attck.nexus`, `attck-reports.attck.nexus`, `attck-empire.attck.nexus`, `attck-mgmt.attck.nexus`, `attck-kasm.attck.nexus`, `attck-wiki.attck.nexus`, `attck-vscode.attck.nexus`, `attck-kali.attck.nexus`. Visiting `https://attck.attck.nexus` from a non-attck.nexus account is rejected at the edge. From an attck.nexus account, the user is redirected to Google, returns with a CF cookie, and lands on the RTPI login page (which still requires Phase 4 to be skipped).

### Phase 4 — JWT verification middleware (`FF_CLOUDFLARE_ACCESS`)
**Goal:** Add [server/auth/strategies/cloudflare-access.ts](../../../server/auth/strategies/cloudflare-access.ts) and wire it into [server/auth/middleware.ts](../../../server/auth/middleware.ts) so RTPI trusts the CF-supplied identity instead of asking for a second login.

Sketch (~80 LOC):
```ts
// server/auth/strategies/cloudflare-access.ts
import { Request, Response, NextFunction } from "express";
import { createRemoteJWKSet, jwtVerify } from "jose";
import { db } from "../../db";
import { users } from "@shared/schema";
import { eq } from "drizzle-orm";

const FF_ENABLED = process.env.FF_CLOUDFLARE_ACCESS === "true";
const TEAM_DOMAIN = process.env.CLOUDFLARE_ACCESS_TEAM_DOMAIN;     // e.g. "rtpi.cloudflareaccess.com"
const AUD_TAGS = (process.env.CLOUDFLARE_ACCESS_AUD_TAGS || "")    // comma-separated; one per app
  .split(",").map(s => s.trim()).filter(Boolean);

const JWKS = TEAM_DOMAIN
  ? createRemoteJWKSet(new URL(`https://${TEAM_DOMAIN}/cdn-cgi/access/certs`))
  : null;

export async function verifyCloudflareJWT(
  req: Request, _res: Response, next: NextFunction
) {
  if (!FF_ENABLED || !JWKS) return next();           // pass-through in dev
  const token = req.header("Cf-Access-Jwt-Assertion");
  if (!token) return next();                         // not behind CF on this path → fall through to other strategies

  try {
    const { payload } = await jwtVerify(token, JWKS, {
      issuer: `https://${TEAM_DOMAIN}`,
      audience: AUD_TAGS,                            // jose accepts string[]
    });
    const email = payload.email as string | undefined;
    if (!email) return next();

    // Upsert user with authMethod='cloudflare_access' (mirrors the Google strategy upsert)
    let user = (await db.select().from(users).where(eq(users.email, email)).limit(1))[0];
    if (!user) {
      [user] = await db.insert(users).values({
        username: email.split("@")[0],
        email,
        authMethod: "cloudflare_access",
        role: "operator",
        isActive: true,
      }).returning();
    }
    (req as any).user = user;
    next();
  } catch {
    next();                                          // bad/expired JWT → let other strategies try
  }
}
```

Wire-up in [server/index.ts](../../../server/index.ts) before existing `passport.session()`:
```ts
import { verifyCloudflareJWT } from "./auth/strategies/cloudflare-access";
app.use(verifyCloudflareJWT);
app.use(passport.initialize());
app.use(passport.session());
```

**Acceptance:** With `FF_CLOUDFLARE_ACCESS=true` set on a deployment fronted by Access, hitting any authenticated route works without a second login round-trip; with the flag off (dev/localhost), behavior is identical to today.

### Phase 5 — Group-to-role mapping (`FF_CLOUDFLARE_ACCESS`)
**Goal:** Replace the hardcoded `role: "operator"` upsert above with a mapping driven by Workspace group membership exposed in the JWT's `groups` custom claim (requires SCIM enabled on the IdP — toggle visible in the screenshots, currently OFF).

Add `shared/access-role-map.ts`:
```ts
export const ROLE_MAP: Array<{ group: string; role: "admin"|"operator"|"viewer" }> = [
  { group: "rtpi-admins",    role: "admin" },
  { group: "rtpi-operators", role: "operator" },
  { group: "rtpi-viewers",   role: "viewer" },
];
```

In Phase-4 middleware, replace the `role: "operator"` literal with `pickRole(payload.groups as string[])` falling back to `viewer`.

**Acceptance:** A Workspace user moved into `rtpi-admins` sees their RTPI role updated to `admin` on next request, with no DB intervention.

### Phase 6 — Direct-OAuth deprecation gate (`FF_CLOUDFLARE_ACCESS` + `FF_DEPRECATE_DIRECT_OAUTH`)
**Goal:** Once a deployment is fully behind Access, refuse direct `/api/v1/auth/google/*` traffic in production to remove the bypass surface.

- Behind both flags, return `404` from the Google OAuth callback route.
- Local dev (`FF_CLOUDFLARE_ACCESS=false`) is unaffected.
- Break-glass: setting `FF_DEPRECATE_DIRECT_OAUTH=false` re-enables the route within seconds without a redeploy.

**Acceptance:** Production deployment with both flags on returns 404 from `GET /api/v1/auth/google` and 401 from any session-based request that lacks a valid CF JWT.

## Operational Runbook

### First-time setup
1. Run [v2.9.4](./v2.9.4-google-oauth-automation.md) once per Workspace tenant. Capture each `(client_id, client_secret, workspace_domain)`.
2. `cd infra/cloudflare-access && cp terraform.tfvars.example terraform.tfvars` — fill in tenants and applications.
3. `export TF_VAR_attck_client_secret=…` (one per tenant).
4. `terraform init && terraform plan` — review.
5. `terraform apply` — IdPs and apps appear in the dashboard.
6. `terraform output access_app_auds` — copy into `CLOUDFLARE_ACCESS_AUD_TAGS` in production `.env`.
7. Set `FF_CLOUDFLARE_ACCESS=true` on the production deployment, redeploy.

### Adding a new app
- Append one entry to the `applications` list in `terraform.tfvars`, `terraform apply`, copy the new AUD tag into `CLOUDFLARE_ACCESS_AUD_TAGS`, redeploy. **No code change.**

### Adding a new tenant
- Run v2.9.4 once for the new Workspace domain. Append to `tenants` in tfvars. `terraform apply`. Existing apps that should also accept the new tenant get the new IdP appended to their `allowed_idps`.

### Rotating a Google client secret
- Mint a new secret in Google Cloud Console (the script does not need to re-run for rotation).
- `export TF_VAR_<tenant>_client_secret=<new>` and `terraform apply` — Cloudflare picks up the new secret transparently to end users.

### Break-glass when Cloudflare edge is down
- Set `FF_CLOUDFLARE_ACCESS=false` and `FF_DEPRECATE_DIRECT_OAUTH=false` on the prod deployment, redeploy. The direct OAuth path comes back; users sign in with the same Google identities, hitting the app callback directly. Once Cloudflare recovers, flip both flags back.

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Cloudflare edge outage locks all users out | Break-glass runbook above; `FF_CLOUDFLARE_ACCESS` is per-deployment, no rebuild required to toggle |
| Group-to-role map silently strips an admin's privileges | Phase 5 logs role transitions; Phase 4 default role is `viewer`, not `none`, so a misconfigured map keeps the user logged in but read-only |
| `cloudflare_zero_trust_access_*` resource renames between provider versions | Pin provider to `>= 4.40, < 5`; track upgrade in v2.10 |
| Workspace SCIM beta instability (groups claim missing intermittently) | Phase 5 falls back to `viewer` rather than rejecting the request |
| Free-tier user cap (50 users) silently exceeded | Add `data "cloudflare_zero_trust_access_seats"` check + alarm in Phase 1 (out of MVP, tracked) |
| Multi-tenant data leakage (one user from `c3s.nexus` reaching `attck.nexus` data) | Phase 2 IdP isolation prevents cross-tenant *login*; row-level tenant scoping is **out of scope here** and tracked under v2.10 |
| Terraform state contains secrets | Use a remote backend with encryption (S3+KMS or Terraform Cloud); never commit local state |

## Out of Scope

- **Multi-tenant row-level scoping.** v2.9.5 isolates *login*; isolating *data* across attck/c3s/d3fend tenants is v2.10.
- **Replacing API-key auth.** [server/auth/strategies/apikey.ts](../../../server/auth/strategies/apikey.ts) remains the path for machine-to-machine traffic that does not transit a browser; CF Access service tokens are an option but not required for v2.9.5.
- **Replacing local auth.** Operators may still use username/password against [server/auth/strategies/local.ts](../../../server/auth/strategies/local.ts) on `localhost`; the production deployment can disable local auth with the existing `DEFAULT_ADMIN_USERNAME`/`DEFAULT_ADMIN_PASSWORD` env-var gating.
- **Non-Google IdPs.** Adding Okta/Entra/SAML is a single new `for_each` block in idp.tf — supported by the same module — but no other tenants are planned for v2.9.5.

## Acceptance Criteria (release-level)

1. `terraform apply` against an empty Cloudflare account produces three IdPs and the eight Access applications declared in `terraform.tfvars.example` (RTPI Dashboard, SysReptor, Empire, Portainer, Kasm mgmt, Docmost, Kasm VS Code, Kasm Kali) — domains aligning row-for-row with `setup/services.manifest`.
2. With `FF_CLOUDFLARE_ACCESS=true`, a user from `attck.nexus` reaching `attck.attck.nexus` is logged in to RTPI without ever seeing the RTPI local login page.
3. A user from `gmail.com` (no matching tenant) is rejected at the Cloudflare edge, never reaches RTPI, and never appears in the `users` table.
4. Toggling `FF_CLOUDFLARE_ACCESS=false` restores the v2.9.4 direct-OAuth flow without a code redeploy.
5. Adding a fourth Workspace tenant is a one-script-run + one-tfvars-edit + one `terraform apply` change. No code modification.
6. Adding a new RTPI surface (e.g. a future ticket-tracker UI) is a one-row append to `setup/services.manifest` + one new application block in `terraform.tfvars` + `terraform apply`. No script changes.
