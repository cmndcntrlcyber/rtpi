# v2.9.5.1 — `catch` browser-recon integration (split-perimeter under Cloudflare Access)

**Created:** 2026-05-06
**Status:** Planning
**Priority:** MEDIUM — sub-release of v2.9.5; required before catch can be used safely in production
**Feature flag:** `FF_CATCH`
**Depends on:** v2.9.5 Cloudflare Access (must land first), v2.9.4 Google OAuth bootstrap (transitive)

## Overview

[`cmndcntrlcyber/catch`](https://github.com/cmndcntrlcyber/catch) is a Node.js browser-fingerprinting and exfiltration service used during authorized engagements to collect client telemetry from targets who land on a phishing or watering-hole page. It is already integrated into rust-nexus as `nexus-recon` (see [rust-nexus/docs/integration/CATCH_TAURI_INTEGRATION.md](../../../rust-nexus/docs/integration/CATCH_TAURI_INTEGRATION.md)); this enhancement brings it onto the parent RTPI side as a first-class containerized service with a clean integration into the v2.9.5 Access perimeter.

Catch is the **only** RTPI surface where the v2.9.5 "everything behind Access" rule must be deliberately broken: targets are not Workspace users and cannot be redirected to a Google login page. The whole point is they don't know they're being instrumented. The mechanism is a split-perimeter:

- **Target-facing hostname** — open to the internet, no Access policy, serves only the fingerprint payload paths.
- **Operator-facing hostname** — gated by Cloudflare Access using the same v2.9.5 IdPs, serves the admin UI and the exfil-sink API.

Both hostnames front the same catch process; Access scoping is per-hostname, not per-path, so a misconfigured policy cannot accidentally expose admin to targets or block targets from the lure.

The work breaks into **6 small phases**, all gated by `FF_CATCH` except Phase 1 (vendoring + Docker, has no public surface).

## Current state analysis

### What exists
- Catch already lives at `cmndcntrlcyber/catch` (fork of `attck-nexus/catch`, MIT-licensed, Node.js 14+).
- Surface: `GET /` (lure), `GET /js/fingerprint.js`, `GET /js/test.js`, `GET|POST /api/fingerprint`, `GET /exfil`, `GET /exfil-frame`, `GET /admin.html`, plus a permissive request handler that accepts every HTTP method.
- Persistence: appends to `access.log` on disk. No DB.
- No authentication anywhere — `admin.html` is reachable by anyone who knows the URL.
- rust-nexus side has `nexus-recon` consuming the catch fingerprint payload via a separate gRPC ingress; that integration is operational and not changing here.

### What RTPI already provides
- v2.9.5 Cloudflare Access perimeter, configured via [infra/cloudflare-access/](../../../infra/) (Phase 1 of v2.9.5).
- `setup/services.manifest` is the single source of truth for public subdomains; `build.sh`, `setup/cert_manager.sh`, and `setup/cloudflare_dns_manager.sh` all iterate it.
- `verifyCloudflareJWT` middleware at [server/auth/strategies/cloudflare-access.ts](../../../server/auth/strategies/cloudflare-access.ts) (Phase 4 of v2.9.5) — admin UI can plug straight in.
- Postgres + Drizzle schema in [shared/schema.ts](../../../shared/schema.ts) — natural home for the `catch_events` replacement of `access.log`.

### What's missing
- Catch is not a Docker service in [docker-compose.yml](../../../docker-compose.yml).
- No subdomains provisioned for either the target-facing or operator-facing hostname.
- Catch's `access.log` is opaque to operators — fingerprints are not surfaced in the RTPI dashboard, not joined to operations/targets, not searchable.
- No mechanism to scope a catch session to an `operation_id`, so events from concurrent engagements share one log file.

## Architecture: split-perimeter

```
                    Target browser                     Operator browser
                          │                                    │
           https://lure.onoiroi.us/...        https://catch-admin.onoiroi.us/...
                          │                                    │
                          ▼                                    ▼
                  Cloudflare edge                      Cloudflare edge
                  (no Access app)                      Access policy: attck IdP
                          │                                    │
                          └──────────────┬─────────────────────┘
                                         ▼
                              Docker: rtpi-catch (Node.js)
                                         │
                                         ▼
                              Postgres: catch_events table
                                         │
                                         ▼
                              RTPI server (existing routes)
                                  /api/v1/catch/*
                                         │
                                         ▼
                              RTPI UI (operator dashboard)
```

The catch container listens on **two** ports inside the docker network: one bound to nginx for the target-facing vhost (port 8080) and one for the operator-facing vhost (port 8081). The Node app routes by `Host` header — only `/api/fingerprint`, `/exfil`, `/exfil-frame`, `/`, and `/js/*` are served on the lure vhost; admin and operator APIs are served only on the admin vhost. A wrong-vhost request returns 404, never the resource.

## Phases

### Phase 1 — Vendor + Docker (`FF_CATCH` not yet relevant)

**Goal:** catch builds and runs inside RTPI's docker-compose with no public surface.

Steps:
1. Add `cmndcntrlcyber/catch` as a git submodule at `services/catch/` (mirrors how `rust-nexus/` is vendored). Pin to a specific commit, not `main`.
2. Add a Dockerfile at `docker/catch/Dockerfile` based on `node:20-alpine`, copying the submodule, running `npm ci --omit=dev`, and starting `node server.js`.
3. Add a `catch` service to [docker-compose.yml](../../../docker-compose.yml) under a new compose profile `catch`, exposing two internal ports (8080 lure, 8081 admin) on the existing internal network. No external port mapping.
4. Pass `BASE_URL`, `LOG_FILE`, `PORT`, `ADMIN_PORT` from environment.

**Verification:** `docker compose --profile catch up -d catch && docker compose exec catch node -e "console.log('ok')"` succeeds. `curl rtpi-catch:8080/` from an adjacent container returns the lure HTML.

Size: ~80 LoC across Dockerfile + compose + .gitmodules.

---

### Phase 2 — Public DNS + TLS for both hostnames (`FF_CATCH`)

**Goal:** `lure.<tenant>.nexus` and `catch-admin.<tenant>.nexus` resolve and serve over TLS, but neither is yet wired through to catch behind nginx.

Steps:
1. Append two rows per tenant to [setup/services.manifest](../../../setup/services.manifest):
   - `lure | catch | http://rtpi-catch:8080 | false | http`
   - `catch-admin | catch | http://rtpi-catch:8081 | false | http`
2. Run `./build.sh --enable-ssl --profile catch` — DNS records and certs provision automatically via the existing manifest iterators.
3. Confirm nginx serves a default 502 (catch service may be off) on both hostnames over TLS.

**Verification:** `dig lure.onoiroi.us` returns a Cloudflare-proxied A record; `curl -I https://lure.onoiroi.us` returns a valid certificate. No catch logic yet.

Size: ~6 manifest rows for 3 tenants. No code.

---

### Phase 3 — Wire catch through nginx with vhost-based path scoping (`FF_CATCH`)

**Goal:** catch responds on both hostnames, with each hostname seeing only its allowed paths.

Steps:
1. In [docker/nginx-ssl.conf](../../../docker/nginx-ssl.conf), add `server` blocks for the two new hostnames. The lure vhost proxies `location /`, `/js/`, `/api/fingerprint`, `/exfil`, `/exfil-frame` to `http://rtpi-catch:8080`; **everything else returns 404**. The admin vhost proxies `/admin*`, `/api/admin/*`, and the operator-side endpoints to `http://rtpi-catch:8081`.
2. In `services/catch/`, add a tiny Express middleware (~30 LoC) at the top of `server.js` that 404s any request whose URL path doesn't match the vhost it arrived on, as defense-in-depth in case nginx ever misroutes. Route by `req.headers.host`.
3. Set the catch container's `ADMIN_PASSWORD` env to a long random string — even though Cloudflare Access will gate the admin vhost in Phase 5, leave catch's local admin auth in place so an internal misroute still requires a secret.

**Verification:** `curl https://lure.onoiroi.us/admin.html` → 404. `curl https://catch-admin.onoiroi.us/admin.html` → 200 (catch login page). `curl https://lure.onoiroi.us/` → catch lure page. `curl https://catch-admin.onoiroi.us/exfil?data=x` → 404.

Size: ~50 LoC nginx + ~30 LoC Express middleware in catch.

---

### Phase 4 — Cloudflare Access on the admin hostname only (`FF_CATCH` + `FF_CLOUDFLARE_ACCESS`)

**Goal:** operators reach the admin vhost through SSO using the same v2.9.5 IdPs; targets reach the lure vhost with no policy in their way.

Steps:
1. In [infra/cloudflare-access/terraform.tfvars](../../../infra/), append one application entry per tenant for `catch-admin.<tenant>.nexus` mirroring the existing RTPI admin app — `auto_redirect_to_identity = true`, `allowed_idps = [tenant_idp]`, policy `email_domain == workspace_domain`, optional require `group = "rtpi-admins"`.
2. **Do not add an Access application for `lure.<tenant>.nexus`.** Verify in the Cloudflare dashboard that no app covers it; the absence of an app is the policy.
3. `terraform apply`. Capture the new AUD tag for the admin app and append to `CLOUDFLARE_ACCESS_AUD_TAGS` in production `.env`.

**Verification:** Visiting `https://catch-admin.onoiroi.us` from a non-onoiroi.us account → rejected at Cloudflare edge with 1003. From an onoiroi.us operator → Google login → catch admin UI loads. Visiting `https://lure.onoiroi.us` from any browser, even one with no CF cookie, loads the lure HTML directly with no redirect.

Size: ~30 lines tfvars across 3 tenants. No code.

---

### Phase 5 — Replace `access.log` with `catch_events` table + RTPI ingest API (`FF_CATCH`)

**Goal:** every fingerprint event lands in Postgres with structured columns, scoped to an `operation_id`, queryable from the RTPI dashboard.

Files: new migration in [migrations/](../../../migrations/), additions to [shared/schema.ts](../../../shared/schema.ts), new route in [server/api/v1/](../../../server/api/v1/), tiny patch to catch's `server.js` to forward instead of file-write.

Steps:
1. Add a Drizzle table:
   ```ts
   export const catchEvents = pgTable("catch_events", {
     id: serial("id").primaryKey(),
     operationId: integer("operation_id").references(() => operations.id),
     campaignSlug: text("campaign_slug").notNull(),
     receivedAt: timestamp("received_at").defaultNow().notNull(),
     sourceIp: text("source_ip").notNull(),
     userAgent: text("user_agent"),
     headers: jsonb("headers").notNull(),
     fingerprint: jsonb("fingerprint").notNull(),
     geo: jsonb("geo"),
     rawPath: text("raw_path").notNull(),
   });
   ```
   Generate migration with `npm run db:generate`.
2. Add `POST /api/v1/catch/ingest` (apikey-strategy gated, no session) accepting the catch event JSON. The route validates the API key, infers `operationId` from `campaignSlug` via a separate `catch_campaigns` table (slug → operation), and inserts.
3. In catch's `server.js`, replace the `access.log` append with a `fetch` to the RTPI ingest URL using a static API key from env. On failure, fall back to local file write so a partitioned RTPI doesn't lose events.
4. Migrate any existing `access.log` content to `catch_events` via a one-shot script in `scripts/migrate-catch-log.ts` if needed.

**Verification:** Hit `https://lure.onoiroi.us/api/fingerprint` with a sample payload; row appears in `catch_events` with the campaign and operation joined. Stop the RTPI server, hit again, confirm fallback file write happens. Restart RTPI and run the recovery script to drain the file into the table.

Size: ~250 LoC across migration + schema + ingest route + catch patch + recovery script.

---

### Phase 6 — Operator dashboard surface (`FF_CATCH`)

**Goal:** operators see catch events in the RTPI UI, scoped to the operation they're viewing, without leaving the main app.

Files: new client routes/components under [client/src/pages/operations/](../../../client/src/pages/operations/) and [client/src/components/catch/](../../../client/src/components/catch/) (new dir).

Steps:
1. Add `CatchEventsPanel.tsx` — a paginated table reading `GET /api/v1/operations/:id/catch-events` and rendering source IP, user agent, geo, and a "fingerprint preview" expandable row.
2. Add a "Catch" tab to the operation detail page; gate visibility on `FF_CATCH`.
3. Add a `catch_campaigns` CRUD UI under `client/src/pages/Settings.tsx` for operators to create campaign slugs, bind them to operations, and copy the lure URL.
4. Optional: live-update the panel via the existing WebSocket channel by adding a `catch.event` event type.

**Verification:** Operator creates a campaign `phishtest-may` bound to operation #42, visits the generated lure URL, confirms a row appears in the operation #42 Catch tab within ~1s. Toggling `FF_CATCH=false` hides the tab and disables ingest writes (returns 503 from the ingest route).

Size: ~400 LoC across UI components + 1 new server route.

## Acceptance criteria (release-level)

1. With `FF_CATCH=true` and the v2.9.5 perimeter applied, `https://lure.onoiroi.us/api/fingerprint` is reachable from any browser with no Cloudflare Access prompt; the response is a 200 with the fingerprint script.
2. `https://catch-admin.onoiroi.us/admin.html` from a non-Workspace browser is blocked at the Cloudflare edge with 1003.
3. From a Workspace operator, the same URL goes through Google login once and lands on catch's admin UI inside the RTPI iframe parent (or directly, depending on dashboard wiring).
4. A target visit produces exactly one row in `catch_events`, joined to the correct `operation_id` via `campaign_slug`.
5. Operator dashboard shows the event under operation detail → Catch tab within 1 second.
6. `FF_CATCH=false` hides the dashboard tab, returns 503 from the ingest route, and breaks the public lure (returns 503) — operators can disable the entire feature without code change.
7. Adding a new tenant or new campaign requires zero code change: services.manifest row + tfvars block + UI form entry.

## Risks & mitigations

| Risk | Mitigation |
|---|---|
| Misrouted nginx exposes admin paths on the lure vhost | Phase 3's vhost-based 404 in catch's Express middleware is defense-in-depth; integration test in Phase 3 verification covers it |
| Cloudflare bot-fight protections trigger on lure subdomain | Lure subdomains marked as orange-cloud but with bot-fight `off` in the per-zone settings; document this in the runbook |
| Targets fingerprint as RTPI infrastructure due to shared TLS cert SANs | Use a separate certificate per lure subdomain; do not multi-SAN with `attck.onoiroi.us` etc. |
| `catch_events.headers` accumulates PII from production targets | Retention policy: cron drops events older than 90 days unless tagged with `retain=true` (out of MVP, tracked under v2.10) |
| Catch container compromised, attacker uses ingest API key as pivot | Ingest endpoint is gated by source-IP allowlist (Docker network only) in addition to API key |
| Phase 5 ingest forward failure causes target events to be silently dropped | Catch falls back to local `access.log` on POST failure; recovery script drains on next deploy |
| Operator forgets to bind a campaign slug, lure events get `operation_id=NULL` | Ingest route returns 400 if `campaign_slug` is unknown, forcing operators to register campaigns before going live |

## Out of scope

- **Lure content authoring.** This release plumbs catch into RTPI; operators still author lure HTML in catch's existing structure or by adding pages to the submodule.
- **Multi-tenant isolation of `catch_events`.** Same as v2.9.5 — login-side isolation only; data-side scoping is v2.10.
- **Replacing rust-nexus's `nexus-recon` gRPC ingress.** That path stays for the C2-side recon flow; this release adds the *RTPI dashboard side* of the same data, not a replacement.
- **Tor / mixnet front-ends for the lure.** v2.10 candidate alongside the rust-nexus mesh comms plan.
