# v3.1.9 — Authentication & Authorization

**Grade: B+** | Target: A | Priority: 9

## Overview

Three auth strategies: local (bcrypt factor 12, account lockout after 5 attempts), Google OAuth 2.0, API keys (SHA256 hashed, expiration, per-key rate limits). RBAC with admin/operator/viewer roles enforced on 40+ routes via `ensureRole()` middleware. Redis-backed sessions with Redis-backed CSRF tokens (1-hour TTL, timing-safe comparison). No fine-grained resource-level permissions. OAuth and API key auth tests are placeholder-quality.

## Evidence

- **Local strategy** (`server/auth/strategies/local.ts`): bcrypt cost factor 12, account lockout (5 failed attempts → 30-minute lock), failed login tracking, last login timestamp.
- **Google OAuth** (`server/auth/strategies/google.ts`): Conditional init (checks credentials), auto-links existing users via email, Empire token init for new OAuth users.
- **API keys** (`server/auth/strategies/apikey.ts`): SHA256 hashing (never stored plaintext), expiration validation, per-key rate limits, last-used tracking. Schema: `apiKeys` table with `keyHash`, `permissions`, `rateLimit`, `expiresAt`, `isActive`.
- **RBAC**: 3 roles (admin, operator, viewer). `ensureRole(...roles)` middleware on 40+ route files. Comprehensive audit logging.
- **Sessions** (`server/auth/session.ts`): Redis-backed, httpOnly cookies, SameSite=lax, environment-aware secure flag.
- **Rate limiting** (`server/middleware/rate-limit.ts`): 500 req/min general, 5 attempts/15min auth, 3 changes/hour password.
- **Gaps**:
  - ~~CSRF in-memory Map~~ — **RESOLVED**: now Redis-backed with 3600s TTL and `secureCompare()` validation
  - No fine-grained resource-level permissions (route-level only)
  - No OAuth or API key auth tests
  - `auth.test.ts` covers CSRF token gen, password rules, bcrypt — but not OAuth/API key flows

### OAuth Tests (Item 3)

Mock Google OAuth callback. Test: new user creation from OAuth → existing user linking via email → session establishment → profile data population.

### Resource-Level Permissions (Item 4)

Currently RBAC is route-level only (admin can access all operations). Add operation-scoped access: operators can only modify operations they own. The `operations` table has an `ownerId` field (FK to `users.id`, NOT NULL). Add `ensureResourceOwnership(table, ownerField)` middleware that checks `ownerId` against the authenticated user (admins bypass). Apply to PUT, POST start/complete, PATCH status routes. DELETE remains admin-only.
