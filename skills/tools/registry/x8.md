# X8

## Overview

X8 (v4.3.2) is a Rust-based HTTP parameter discovery fuzzer written by sh1yo. It brute-forces web applications to uncover hidden or undocumented parameters in query strings, POST bodies, JSON payloads, and custom headers. The tool works by injecting candidate parameter names from a wordlist and detecting successful discoveries through response analysis—comparing status codes, content length, response time, header changes, and parameter reflection. X8 is optimized for speed with async requests and is particularly effective against APIs and web apps with poor parameter documentation or legacy debug endpoints.

## When to use

Use X8 during the reconnaissance and enumeration phase of web application testing when you need to discover hidden attack surface. Deploy it after initial crawling/spidering to find parameters not visible in client-side code or documentation. Ideal for: REST/GraphQL APIs with minimal documentation; admin panels or authenticated areas where functionality may be hidden; applications suspected of having debug/test parameters; targets where you have valid session tokens but limited knowledge of available endpoints. X8 is most valuable when you have exhausted passive reconnaissance and need active brute-force discovery. Not recommended for: static websites with no dynamic parameters; applications with strict rate-limiting or aggressive WAFs; initial triage of large scope (too noisy).

## Authentication & setup

X8 is pre-installed at `/opt/tools/bin/x8` in RTPI. No additional installation or configuration required. For authenticated testing, pass session cookies via `--headers 'Cookie: session=...'` or use `-H` flag. If testing requires custom headers (API keys, tokens), specify with `--headers 'Authorization: Bearer TOKEN'`. For targets behind proxies, use `--proxy http://127.0.0.1:8080` (e.g., Burp). No credentials are stored by the tool itself; all auth must be passed per-invocation. Verify tool is functional with `x8 --help`. Ensure you have appropriate wordlists in `/opt/wordlists/` or similar; X8 does not include default wordlists.

## Key commands / parameters

Core invocation: `x8 [flags] -u <URL> -w <wordlist>`

Critical flags:
`-u <URL>` — Target URL (required)
`-w <wordlist>` — Parameter wordlist path (required; use SecLists parameters-*.txt)
`-P <type>` — Parameter type: query, body, headers, json (default: query)
`-X <method>` — HTTP method: GET, POST, PUT, etc. (default: GET)
`--headers <string>` or `-H` — Custom headers (e.g., 'Cookie: ...', 'Authorization: ...')
`-o <file>` — Save discovered parameters to file
`--delay <ms>` — Delay between requests in milliseconds (rate limiting)
`--status-code-filter <codes>` — Only report specific status codes (e.g., 200,201)
`--reflected-only` — Only report parameters whose values are reflected in response
`--disable-response-correction` — Disable smart diffing (faster but less accurate)
`--verify` — Re-verify discoveries with random values to reduce false positives
`--proxy <URL>` — Route traffic through proxy
`--max <num>` — Max parameters to discover before stopping

Example: `x8 -u https://api.target.com/v1/users -w params.txt -P json -H 'Authorization: Bearer TOKEN' --verify -o found.txt`

## Example workflows

**Basic query parameter discovery:**
`x8 -u 'https://target.com/search?q=test' -w /opt/wordlists/params.txt -o query-params.txt`

**JSON parameter fuzzing for API:**
`x8 -u https://api.target.com/endpoint -w api-params.txt -P json -X POST -H 'Content-Type: application/json' --verify`

**Authenticated POST body parameter discovery:**
`x8 -u https://target.com/admin/update -w params.txt -P body -X POST -H 'Cookie: session=abc123' --delay 100`

**Custom header discovery:**
`x8 -u https://target.com/ -w headers.txt -P headers --reflected-only`

**Rate-limited testing with verification:**
`x8 -u https://target.com/api/v2/data -w params.txt -P query --delay 500 --verify --status-code-filter 200,201,202 -o verified.txt`

**Through Burp Suite for inspection:**
`x8 -u https://target.com/endpoint -w params.txt --proxy http://127.0.0.1:8080`

Typical workflow: Run against each interesting endpoint discovered during crawling → review output for sensitive parameters (debug, admin, test, internal) → manually test each discovery for exploitable behavior.

## Output format

X8 writes discovered parameters to stdout in real-time, one per line, typically formatted as:
`[FOUND] parameter_name` or `parameter_name (reflected)` if reflection detected.

When `-o <file>` is used, output is saved line-by-line to the specified file for later processing. Output includes only parameter names, not full requests or responses. For detailed analysis, route through proxy (`--proxy`) and inspect in Burp/ZAP.

No JSON or structured output format by default; post-process with grep/awk/sort/uniq as needed. The tool does not provide exploitation payloads or vulnerability assessment—it only reports discovered parameter names. Exit code 0 on successful completion; non-zero on error.

## Common pitfalls

**Noisy and detectable:** X8 generates large volumes of HTTP requests (one per wordlist entry). Easily detected by WAFs, IDS, or monitoring systems. Always use `--delay` in production environments.

**False positives:** Without `--verify`, dynamic content or non-deterministic responses can cause false discoveries. Always re-verify findings manually or use `--verify` flag.

**Wordlist dependency:** Effectiveness entirely depends on wordlist quality. Generic lists miss application-specific parameters. Curate wordlists based on target technology (e.g., PHP vs .NET vs Node.js parameters differ).

**No automatic exploitation:** X8 only discovers parameter names. You must manually test each for IDOR, injection, auth bypass, etc. Do not assume discovered parameters are exploitable.

**Session expiration:** Long-running scans may outlive session tokens. Monitor for authentication errors mid-scan; re-run with fresh tokens if needed.

**Rate limiting/account lockout:** Aggressive scanning can trigger account lockouts or IP bans. Test throttling settings on non-critical accounts first.

**POST body vs JSON confusion:** Ensure `-P` type matches actual application behavior (application/x-www-form-urlencoded vs application/json). Mismatched types yield no results.

**Missing baseline:** Response diffing requires stable baseline. If target has timestamps, CSRF tokens, or dynamic ads, use `--disable-response-correction` and filter manually.
